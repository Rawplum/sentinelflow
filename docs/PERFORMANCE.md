# 性能与并发实测

这份文件只记录**实际测到的数字**。没有测的项目写"未测量"，不写估计值。

## 1. 环境

| 项 | 值 |
| --- | --- |
| 操作系统 | Windows 10.0.22631 |
| Python | 3.11.4 |
| 数据库 | PostgreSQL 16.15（本机集群，端口 55432，`--locale=C`） |
| 服务 | uvicorn 单进程单 worker |
| 客户端 | 单进程、串行、keep-alive HTTP，连本机回环 |
| 数据集 | 全部合成，`perf/dataset.py` 按种子生成 |

**这份数字不能外推**：单机回环、无网络延迟、无 TLS、单 worker。它回答的是"代码里有没有
明显的瓶颈"，不是"生产环境能扛多少 QPS"。吞吐量没有报告——串行客户端测出来的吞吐量
描述的是客户端，不是服务端。

## 2. 测试数据

`perf/dataset.py`，种子固定为 `20260301`，同一规模两次生成的数据完全相同。

- **告警簇**：每 10 分钟一个"爆发"——同一 `username + source_ip` 在 5 分钟内 6 次失败登录，
  因此每个簇恰好产出一个告警。检测规则要求 5 次，这里给 6 次留余量。
- **噪声**：每簇之间穿插 10 条成功登录、单次失败、文件访问，来自随机账号，
  这样 `outcome=success`、`username=...` 这些过滤条件才有真实的选择性。
- **有界基数**：200 个用户名、99 个 IP、20 个资产——这是 `(username, source_ip)` 分组和
  复合索引有意义的前提。
- **批量插入**：每 5000 行一条 `INSERT`，96k 行约 5 秒。

三个规模：

| 规模 | 事件数 | 告警数（检测后） |
| --- | --- | --- |
| 小 | 1 750 | 100 + 1 |
| 中 | 16 150 | 1 000 + 1 |
| 大 | 96 150 | 6 000 + 1 |

> "+1" 是额外播种的一个含 150 条证据的告警，用来测报告上限（上限是 100 条）。

## 3. 方法

```bat
python -m perf.runner --alerts 6000 --iterations 20     :: 延迟
python -m perf.concurrency                              :: 并发与超时
```

`perf/runner.py` 每次运行都：删库重建 → 播种 → 启动**真实 uvicorn 进程** → 登录 →
逐场景发请求 → 关闭。每个场景先发一次不计时的预热请求，再计时 N 次。
`perf/concurrency.py` 用多线程客户端打同一个接口。

指标定义：P50 是中位数，P95 用最近秩法，`err%` 是 HTTP ≥400 的比例，
`resp KB` 是该场景返回体的最大字节数。

## 5. 发现并修复的问题

### 5.1 检测的写入路径：每个告警 9 次往返

**现象**：96k 事件、6 000 个新告警时，`POST /detections/run` 要 **25.6 秒**。

**定位**：`cProfile` 显示扫描部分只占 2.2 秒，其余全在写。原实现对每个告警做
`SAVEPOINT` → `INSERT alert` → 每条证据一次 `INSERT`（经 ORM 关联表）→ `RELEASE`，
6 000 个告警约 5.4 万次往返。

**修复**（`services/detection.py::_insert_alerts`）：把整批放进**一个** savepoint，
`add_all` 一次 flush，证据关联用一条 `insert(alert_events)` 批量写入。
并发撞 dedup key 时整批回滚，退回原来的逐条路径——罕见情况行为不变。

**结果**：96k 事件下 **25.6 s → 3.0 s**（约 8.4 倍）。同一份数据、同一台机器。

### 5.2 并发改状态：历史链断裂

**现象**：8 个客户端各 6 轮同时 `PATCH /alerts/{id}`，历史里出现
"上一行结束于 investigating，下一行却从 open 开始"。

**原因**：`change_status` 先 `session.get(Alert)` 读状态，再判断、再写，中间没有任何东西
阻止第二个请求读到同一个旧状态。

**修复**：`session.get(Alert, alert_id, with_for_update=True)`，把"读-判断-写"放进同一个行锁。

**结果**：修复后同样 8×6 并发，历史始终是一条从 `open` 出发、末端等于 `alert.status` 的链。

> **限制**：SQLite 忽略 `FOR UPDATE`。SQLite 只用于跑测试，不是部署目标（见 README）。
> 因此这两条回归测试在 SQLite 下会被跳过，只在 PostgreSQL 下执行。

### 5.3 并发发起调查：一个告警起了 5 个任务

**现象**：3 个告警、每个 6 个并发 `POST /investigations`，总共接受了 5 个（应为 3 个）。

**原因**：同样的问题——查"有没有在跑的"和插入新任务之间没有原子性。

**修复**：同样加行锁，在 `create_investigation` 开头锁住告警行。

**结果**：修复后 3 个告警 × 6 并发 = 恰好 3 个被接受、15 个 409，
且数据库里同一告警的两次调查时间区间**不重叠**。

### 5.4 批量导入后统计信息过期：查询慢 20 倍

**现象**：96k 事件刚导入完，`GET /events?offset=20000` 的 P95 是 **515 ms**；
跑一次 `ANALYZE` 之后同样的请求是 **16.7 ms**。

**原因**：PostgreSQL 的自动分析还没触发，规划器按导入前的行数估算，选了顺序扫描 + 全排序。

**处理**：`perf/runner.py` 现在把这一步**显式测量**（`events:deep_page_cold` vs `events:deep_page`），
并在批量导入后执行 `ANALYZE`。生产侧的建议写进了 §7：批量导入后跑一次 `ANALYZE`。

## 6. 没有修的部分（有数据支撑的判断）

| 现象 | 数字 | 为什么不修 |
| --- | --- | --- |
| 关键字搜索是全表扫描 | 96k 时 P50 39 ms | `ILIKE '%x%'` 无法用 B-tree。要修得装 `pg_trgm` 扩展 + GIN 索引，那是一个部署依赖，而 39 ms 在可接受范围 |
| `count(*)` 随过滤走全表 | 96k 时约 19 ms，占过滤查询的一半 | 非选择性过滤（51k/96k 命中）本来就不适合索引；换成估算会牺牲准确性 |
| 深分页 OFFSET 是 O(n) | offset 20000 时 15 ms | 要根治得换 keyset 分页，会改 API 契约；当前延迟不构成问题 |
| 检测仍要全表扫描 | 96k 时扫描占 2.2 s | 已按 `event_type/action/outcome` 过滤并有复合索引；进一步优化需要列投影，收益约 0.4 s，暂时不值得 |
| 检测返回 6 000 个 ID（228 KB） | 见 §4 | 6 000 个新告警本身已是极端场景；改契约的收益小于风险 |

## 7. 运维建议（来自实测，不是猜测）

1. **批量导入后执行 `ANALYZE security_events`**。不做的代价是 20 倍（§5.4）。
2. 单次检测会扫全表：96k 事件约 3 秒。事件量到百万级时应改为增量检测（按时间窗口），
   而不是加缓存。
3. 报告响应固定约 50 KB（100 条证据封顶），不会随表增长——这是上限生效的证据。

## 8. 局限

- 单机回环、单 worker、无并发读负载。没有测多客户端同时读的吞吐。
- 只有 PostgreSQL 16，没有测其他版本或 SQLite 的性能（SQLite 不是部署目标）。
- 数据集是合成的规则化数据，真实日志的分布（长尾账号、突发洪水）没有覆盖。
- 并发场景只覆盖了三种：状态更新、发起调查、模型超时。没有测同时导入 + 检测 + 查询。
- 延迟包含 Python 客户端与 HTTP 序列化的开销，比纯服务端处理时间略高。
- 机器是开发机，后台还有别的进程；同一场景两次运行可能差 20%–40%（见 §5.1 的 25.6 s
  与 17.8 s 两个观测值）。
